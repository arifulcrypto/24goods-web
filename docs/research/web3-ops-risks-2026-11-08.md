# Web3 authorization, supplier trust and runtime security evidence

Research date: 2026-11-08 UTC. Read-only research for 24goods; no installs, exploits, live-wallet activity or application changes. Read AGENTS.md and the progress hand-off. This evidence does not establish a vulnerability or compromise in 24goods and does not satisfy its independent pentest gate.

Legend: **Verified** = directly checked primary publication or metadata, within the stated scope; **Reported** = a named primary investigator's finding, not independently reproduced here; **Inferred** = proposed application to 24goods; **Unverified** = insufficient independent evidence. Verification of a publisher or report is not verification of every underlying claim.

## 2. A genuine key or valid signature can authorize a harmful operation

**Verified primary incident statement:** Bybit's February 26, 2025 statement says a Safe developer's compromised credentials allowed access to Safe infrastructure and deceived signers into approving a malicious transaction. It reports no indication of compromise within Bybit infrastructure from Verichains/Sygnia's preliminary review, and links their reports. This supports an authorization/interface compromise example without asserting that wallet private keys were stolen or that cryptography failed. Sygnia's own blog returned 403 here; mirrored PDFs were discovered but are not needed as the authority for this claim. [Bybit primary statement](https://www.bybit.com/en/press/post/bybit-confirms-security-integrity-amid-safe-wallet-incident-no-compromise-in-infrastructure-blt9986889e919da8d2).

**Verified guidance:** Safe recommends independent transaction checks, separate devices, multiple decoding/simulation/hash-verification tools, and trusted contract lists. A genuine site and normal-looking UI do not replace inspection of the actual signed intent. [Safe verification guidance](https://help.safe.global/articles/2485383995-how-to-perform-basic-transactions-checks-on-safewallet).

**Verified mechanisms:** Address poisoning attempts to make users copy a lookalike recipient from transaction history. Signed approvals/Permit2 phishing can grant an attacker spending authority without exposing the seed. ERC-2612 standardizes signature-based allowance changes with owner, spender, value, nonce, deadline and domain separation; support depends on the specific token/contract. Do not claim every USDT deployment implements ERC-2612. [MetaMask poisoning guidance](https://support.metamask.io/id/stay-safe/protect-yourself/wallet-and-hardware/address-poisoning-scams/), [MetaMask signature-phishing guidance](https://support.metamask.io/privacy-and-security/staying-safe-in-web3/signature-phishing/), [ERC-2612 specification](https://eips.ethereum.org/EIPS/eip-2612).

**Inferred for 24goods:** Authentication proves the presented authority; authorization must still bind tenant, actor role, object, amount, currency, recipient, operation, state, expiry, version and idempotency key. Review valid-credential abuse, compromised staff/API tokens, replay, reordered calls, midnight/expiry transitions, and cumulative ledger invariants. Never accept a callback signature as proof of settlement. A compromised provider can sign misleading data, so supplier truth must also be reconciled against independent evidence or an explicit trust boundary.

## 3. Proactive supplier and package cross-check

**Verified metadata, research-time snapshot:** A direct HTTPS read of the npm registry for `bitkub-trading-mcp-official` returned `latest=1.0.1`, maintainer `rd09`, and publication on 2026-10-03. Its exposed version metadata contained no `postinstall` script; only the default test script appeared. This corroborates GCSA's ownership/version warning while providing **no evidence of malicious code execution or stolen keys**. No tarball was downloaded or executed. The original official API-doc repository was accessible; the linked MCP repository currently returned 404. Search results from stale/forked documentation are not proof of present vendor ownership. [npm package metadata](https://registry.npmjs.org/bitkub-trading-mcp-official), [Bitkub API-doc repository](https://github.com/bitkub/bitkub-official-api-docs).

**Inferred control:** Before trusting a gateway, wallet, SDK, MCP tool or RPC provider, record its legal/vendor identity, canonical domains, support channel, official repository, publisher ownership, exact version/digest, release/advisory history and allowed capabilities. Cross-check at least vendor documentation plus package/repository provenance; a name containing `official` is insufficient. Pin artifacts and validate ownership/provenance when upgrading. Review release/install scripts without running them in a secrets-bearing process. Require read-only API permissions where writes are unnecessary and avoid withdrawal authority. Alert on publisher changes, yanked releases, stale integrations, unexpected endpoint changes, overdue patching and key rotation/revocation failures.

## 4. USDT identity and chain-specific finality

**Verified:** Tether publishes network-specific identifiers, including TRON USD₮ `TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t`. USDT0's own deployment registry lists Arbitrum One chain ID 42161 with token `0xFd086bC7CD5C481DCC9C85ebE478A1C0b69FCbb9`; OKX documents USDT0 integration with X Layer. Thus Tether's direct-issuance list alone is insufficient to classify every bridged/omnichain variant. Do not silently substitute USDT, USDT0, an old bridge token or another contract with the same symbol. These are research examples, not instructions to change live configuration. [Tether supported protocols](https://tether.to/en/supported-protocols/), [USDT0 deployment registry](https://docs.usdt0.to/technical-documentation/deployments), [OKX X Layer/USDT0 announcement](https://www.okx.com/learn/tether-usdt0-on-x-layer-and-okx).

**Verified:** TRON distinguishes broadcast, inclusion, execution receipt and solidified receipt; solidification alone still does not prove smart-contract execution succeeded. Arbitrum distinguishes sequencer soft confirmation (`latest`) from parent-chain `safe` and `finalized` states. A transaction hash, screenshot, token name or an RPC success response is insufficient settlement evidence. [TRON confirmation semantics](https://developers.tron.network/docs/confirmation-semantics), [Arbitrum finality/reorg documentation](https://developer.arbitrum.io/how-arbitrum-works/reference/finality-and-reorgs).

**Inferred acceptance criteria:** Version each supported payment network's chain ID, exact accepted token contract/variant, decimals, recipient ownership, receipt/event validation, minimum amount policy, confirmation/finality rule and RPC/indexer trust assumptions. Store durable `(chain, tx_hash, log_index)` identities and block hashes, reconcile against the invoice and exact integer units, reject failed receipts/wrong tokens/wrong chain/duplicates, and handle reorgs or provider disagreement explicitly. Prefer an independent node/provider for reconciliation when feasible; two URLs from one shared backend are not independent. If BEpusdt does not expose evidence required by the settlement policy, document that assurance gap before real payments.

## 5. PHP2Shell, LXD and runc are separate advisories

| Primary advisory | Verified identity and first-fixed examples | Scope and limitation |
| --- | --- | --- |
| [PHP Foundation, 2026-10-21](https://thephp.foundation/blog/2026/10/21/todays-php-security-release-and-how-were-strengthening-php-security/) | PHP2Shell: CVE-2026-109618 (OOM memory corruption) and CVE-2026-109619 (stale global state). Releases 8.2.35, 8.3.36, 8.4.27, 8.5.12 fixed the original issues. | Core PHP, with unauthenticated RCE demonstrated under described execution paths. These are first-fixed baselines, not a universal current-version recommendation. Runtime/library exposure must be inventoried; 24goods uses Python/Go and is not thereby proved affected. |
| [Canonical LXD, 2026-11-04](https://github.com/canonical/lxd/security/advisories/GHSA-99jp-jwmc-65p4) | CVE-2026-112816 / GHSA-99jp-jwmc-65p4, authentication bypass through unverified client-certificate chains. Advisory lists patched 4.0.15, 5.0.11, 5.21.9, 6.10.0, 6.10.1. | TLS only proved possession for the first certificate, but authorization matched other client-supplied certificates against trust. Public trusted certificates could be accepted without corresponding private keys. Restrict HTTPS-listener reachability and use a vendor-fixed release; no configuration-only fix is claimed. This is an authentication bug, not a demonstrated stolen-key attack. |
| [runc maintainer, 2025-11-05](https://github.com/opencontainers/runc/security/advisories/GHSA-qw9x-cqr3-wc7r) | CVE-2025-52565; published with CVE-2025-31133 and CVE-2025-52881. First-fixed branches 1.2.8, 1.3.3, 1.4.0-rc.3. | Container escape/host-impact conditions involve mounts/races and attacker capabilities. runc is an OCI runtime; LXD's management/certificate issue is separate. Advisory publication alone does not prove active exploitation or that this host is vulnerable. |

**Verified follow-up:** PHP's October 23 response describes a distinct `session.upload_progress`/runtime serializer-change vector (CVE-2026-115560), requiring an unusual configuration/application combination. The initial fixes remain necessary; the initial PHP2Shell release alone is not assurance against every later finding. [PHP's official news archive, October 23 advisory](https://www.php.net/archive/2026.php).

**Inferred operations:** Maintain a deployed inventory for host kernel, container runtime/daemon, proxy, language runtimes, database/Redis, BEpusdt and frontend build chain. Use supported vendor packages and their backport status, rather than raw version-string comparison alone. Record owner, first-fixed/advisory version, deployed digest, last check, restart/recreate verification and next review date. Key inventory should contain key IDs/fingerprints, holder/service, scope, owner, issuance/expiry/rotation/revocation dates and tested rollback dependencies; never secret values. Rotate/revoke promptly on exposure or supplier compromise and verify old credentials are rejected. Updating binaries does not remove prior attacker persistence or revoke leaked credentials.
