# External payment/security research for 24goods

Checked 2026-11-07. Read-only: public documentation/source requests only; no exploitation, payment submission, production load, credentials or GitHub mutations. Repository context read: AGENTS.md, docs/progress.md, docs/architecture.md, docs/analysis.md. This is external research, not an audit result for 24goods.

Legend: **V** = directly verified in the linked primary documentation, maintainer advisory or current source; a published advisory verifies the publisher's finding, not independent reproduction. **I** = our inference/recommendation. **U** = not verified/access unavailable. Source code is pinned to the retrieved main-branch SHA where possible. No upstream code was copied into 24goods.

## 1. Provider configuration and safe callback patterns

### Sub2API — useful design reference, not a security baseline

Current main SHA: `6b4b37db43443b5e88e424fe3c69602cc3810dfb`.

- **V:** EasyPay takes `pid`, `pkey`, `apiBase`, `notifyUrl`, `returnUrl` per instance. Its callback verifier allowlists parameter names, rejects `&`/`=` inside non-name values, verifies the signature, and binds `pid` to the configured merchant. `ConfirmNotification` then queries that instance's own gateway/credentials and checks paid status, amount and gateway trade number. It parses money as float and allows a tolerance, so it does not satisfy 24goods' exact-Decimal invariant as written. [EasyPay provider, configuration and callbacks](https://github.com/Wei-Shaw/sub2api/blob/6b4b37db43443b5e88e424fe3c69602cc3810dfb/backend/internal/payment/provider/easypay.go#L53).
- **V:** Orders carry a provider identity snapshot: provider instance, provider key, payment mode, merchant/app identity and currency. Metadata validation checks identity against that snapshot. Webhook resolution uses the order's original provider instance; ambiguous multi-instance fallback is rejected. This is an identity snapshot, **not** a complete immutable copy of endpoint/secret configuration: the resolver still loads the current instance. [Snapshot implementation](https://github.com/Wei-Shaw/sub2api/blob/6b4b37db43443b5e88e424fe3c69602cc3810dfb/backend/internal/service/payment_order_provider_snapshot.go#L13), [webhook instance resolution](https://github.com/Wei-Shaw/sub2api/blob/6b4b37db43443b5e88e424fe3c69602cc3810dfb/backend/internal/service/payment_webhook_provider.go#L31).
- **V:** Routing supports round-robin / least-amount and min/max/daily usage filters, counting pending payments in usage. When all candidates exceed limits it falls back to the full candidate list; these are routing preferences, not strict financial caps. [Load balancer](https://github.com/Wei-Shaw/sub2api/blob/6b4b37db43443b5e88e424fe3c69602cc3810dfb/backend/internal/payment/load_balancer.go#L18).
- **V:** Despite an outdated schema comment saying encrypted configuration, new provider configurations are serialized as plaintext JSON; decryption supports legacy AES ciphertext only during migration. Deletes are refused while the instance has pending orders. [Actual persistence functions](https://github.com/Wei-Shaw/sub2api/blob/6b4b37db43443b5e88e424fe3c69602cc3810dfb/backend/internal/service/payment_config_providers.go#L526).
- **I:** 24goods should use separate provider-instance identity, immutable/versioned configuration references per payment attempt, retirement rather than deletion while attempts can settle, and encrypted server-only secrets. Provider changes should not reinterpret in-flight attempts. Keep exact Decimal and strict caps rather than importing upstream tolerance/fallback semantics.

### New API — configurable EPay and transactional completion; do not copy return behaviour

Current main SHA: `dd50ee0a567b810ea60e74dcd9ea6a5786b37b91`.

- **V:** `PayAddress`, `EpayId`, `EpayKey`, plus an optional callback address are server settings. `GetEpayClient` creates the EPay SDK client using that configured URL and merchant credentials. This demonstrates configurable EPay-compatible providers, not proof of arbitrary vendor compatibility. [Settings](https://github.com/QuantumNous/new-api/blob/dd50ee0a567b810ea60e74dcd9ea6a5786b37b91/setting/operation_setting/payment_setting_old.go#L12), [client creation](https://github.com/QuantumNous/new-api/blob/dd50ee0a567b810ea60e74dcd9ea6a5786b37b91/controller/topup.go#L137).
- **V:** `RechargeEpay` uses a database transaction + order row lock, checks provider/status, changes the order state and credits the user in that transaction. The process-local order mutex is explicitly only an optimization. The function receives no callback amount/currency or gateway trade identifier, so it is not evidence of the full 24goods binding/re-query pipeline. [Atomic recharge](https://github.com/QuantumNous/new-api/blob/dd50ee0a567b810ea60e74dcd9ea6a5786b37b91/model/topup.go#L173).
- **V:** The subscription browser-return handler verifies the signed return parameters and calls `CompleteSubscriptionOrder` when the return says success. This conflicts with 24goods' return-URL-never-fulfils invariant. [Return handler](https://github.com/QuantumNous/new-api/blob/dd50ee0a567b810ea60e74dcd9ea6a5786b37b91/controller/subscription_payment_epay.go#L173).

### BEpusdt — multiple watch addresses and allocation are verified; round-robin is not

Current main SHA: `78db081b3527c7c6a4763e853255dd9141b3bcae`.

- **V:** Wallet records contain address, normalized match address, trade type and enabled status, with a unique match-address/trade-type index. Available wallets are filtered by trade type + enabled status. The reviewed wallet model has no private-key field. [Wallet model](https://github.com/v03413/BEpusdt/blob/78db081b3527c7c6a4763e853255dd9141b3bcae/app/model/wallet.go#L19).
- **V:** `CalcTradeAmount` considers waiting/confirming address+amount pairs occupied, tries each wallet for the requested amount, then increments by atomic precision and retries. Address-exclusive mode selects an address without another active exclusive order and returns amount zero. Neither reviewed function implements round-robin, weighted rotation, per-address daily caps, or key derivation. [Allocation](https://github.com/v03413/BEpusdt/blob/78db081b3527c7c6a4763e853255dd9141b3bcae/app/model/order.go#L373).
- **V:** The callback contract distinguishes waiting (`1`), paid (`2`), expired (`3`); only paid settles. Native callback data includes fiat amount, actual crypto amount, receiving address and block transaction ID. The EPay callback path is GET with a five-second HTTP client timeout, and considers a 200 body containing `success` or `ok` acknowledged. [Callback documentation](https://github.com/v03413/BEpusdt/blob/78db081b3527c7c6a4763e853255dd9141b3bcae/docs/notify/readme.md), [notifier implementation](https://github.com/v03413/BEpusdt/blob/78db081b3527c7c6a4763e853255dd9141b3bcae/app/task/notify/notify.go#L27).
- **V:** Documentation describes exact, prefix, and rounded amount matching. It also explains an earlier prefix-matching bug: normalized `1.50` became `1.5`, which matched a distinct `1.51` payment, taking another order's payment. Current documentation says padding to atomic precision fixes that ambiguity. [Matching modes and historical flaw](https://github.com/v03413/BEpusdt/blob/78db081b3527c7c6a4763e853255dd9141b3bcae/docs/payment-match-mode/README.md).
- **I:** A wallet rotation feature needs an explicit deterministic scheduler/lease, chain+asset+address+amount binding, persisted upstream trade/transaction IDs and old-address monitoring through late-payment windows. Disabling an address for new orders should not erase its outstanding obligations. This is design guidance, not a verified current capability of 24goods or BEpusdt.

### Dujiao-Next and established commerce references

Current Dujiao main SHA: `7d0b44e604b36e1e17e81b620ff8d78c8851390e`.

- **V:** Dujiao's channel model separates provider type, channel/payment method, interaction mode, fees, limits, configuration, enabled state and sort order. Its EPay config supplies gateway URL, merchant identity, version/signing settings; callback verification chooses MD5 vs RSA from server configuration and separately checks merchant ownership. [Channel model](https://github.com/dujiao-next/dujiao-next/blob/7d0b44e604b36e1e17e81b620ff8d78c8851390e/internal/modules/payment/domain/channel.go#L12), [EPay adapter](https://github.com/dujiao-next/dujiao-next/blob/7d0b44e604b36e1e17e81b620ff8d78c8851390e/internal/modules/payment/infrastructure/gateway/epay/epay.go#L295).
- **V:** Saleor isolates gateway implementation in Payment Apps and maintains a consistent core transaction/status API. Its payment model defines database uniqueness for transaction event idempotency. These are architectural references, not evidence of native EPay support. [Saleor Payment Apps](https://docs.saleor.io/developer/payments/payment-apps), [payment model](https://github.com/saleor/saleor/blob/main/saleor/payment/models.py).
- **V:** Medusa's merged July 22, 2026 fix serializes capture/refund and promotion budget guards using row locks and rereads within the transaction; integration tests cover concurrent requests. Provider network calls occur after the relevant transaction commits. [Merged PR #16097](https://github.com/medusajs/medusa/pull/16097).
- **I:** Keep payment method (Alipay, WeChat, USDT-chain) separate from provider instance. Use one settlement state machine across providers; adapters normalize transport/signing/status only. A successful HTTP response or scanner alert alone does not establish fulfilment bypass.

## 2. Xiaodou documentation investigation

- **V:** [Requested page](https://pay.xiaodouap.cn/app/open-platform/docs) returns HTTP 200 to a normal HTTPS GET but contains a Vite SPA shell. The web browsing tool could not extract it; public JavaScript was then inspected through standard GET requests.
- **V:** The [public documentation-page bundle](https://pay.xiaodouap.cn/app/assets/OpenPlatformDocsPage-unLbb5_K.js) explicitly says documentation is visible after login. It loads a catalogue/content through portal APIs, and exposes metadata fields for API schema version, request/response/webhook signature-spec versions, package hashes and document packages. It does not contain the actual payment/signature contract.
- **V:** The main bundle maps catalogue retrieval to `/api/open/portal/docs`, with separate document content/download and skill-package routes. Public route names are implementation observations, not permission to access protected documents.
- **V:** A single normal unauthenticated GET to [the catalogue endpoint](https://pay.xiaodouap.cn/api/open/portal/docs) returned HTTP 401 with `NO_AUTH_TOKEN` / no authentication token. Investigation stopped at that boundary.
- **U:** Actual merchant contract, EPay compatibility/version, endpoints, algorithm/canonicalization, query semantics, required identifiers, callback retry/ACK, timestamp/replay protection, refund support, merchant limits and operational reliability remain unverified. No login bypass or account mutation was attempted.
- **I:** Obtain the merchant-provided current document archive/example package through an authorized login/export; verify its published hashes/version; add offline protocol fixtures before enabling a real provider. Do not infer Xiaodou compatibility from the EPay name or other projects' generic adapters.

## 4. Primary operational guidance

- **V:** [Stripe webhook guidance](https://docs.stripe.com/webhooks) requires raw-payload signature verification, pinned current signature scheme and constant-time comparison; signed timestamp default tolerance is five minutes, and duplicate events/order independence still require application handling. Provider retries can carry new signatures/timestamps. **I:** Timestamp recency is not durable transaction idempotency. EPay without signed timestamp still needs durable deduplication and re-query; do not invent a timestamp requirement unsupported by its contract.
- **V:** [OWASP upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) recommends type/extension allowlists, generated names, size limits, authorized uploads, storage outside webroot/separate server, maintained parsers and defense in depth; MIME and magic checks alone are insufficient. **I:** Resource limits should cover decompressed image dimensions, decode cost and storage quota, plus authorized retrieval.

## 6. Urgent deployment-specific BEpusdt ACK finding

Checked the exact upstream revision named by `deploy/docker-compose.yml:143-144`: short `0716485`, resolved full SHA `07164853c38ed43700d3abcaab78e832782d36fa` (v1.24.3 image digest pinned locally).

- **V:** Native JSON POST `epusdt()` checks **only HTTP status == 200**, never reads the response body, and then calls `SetNotifyState(OrderNotifyStateSucc)` at lines 148-155. Therefore HTTP 200 with body `fail` is acknowledged as success. This differs from the **EPay GET** path, which checks body text. [Pinned native ACK source](https://github.com/v03413/BEpusdt/blob/07164853c38ed43700d3abcaab78e832782d36fa/app/task/notify/notify.go#L148).
- **V:** The three-second retry task queries failed trade orders and calls the notifier when backoff allows. [Pinned retry task](https://github.com/v03413/BEpusdt/blob/07164853c38ed43700d3abcaab78e832782d36fa/app/task/notify.go#L14). Its DB query includes `status = success`, `notify_state = fail`, and retry-count limit, so an order marked notification-success is excluded. [Pinned retry-selection query](https://github.com/v03413/BEpusdt/blob/07164853c38ed43700d3abcaab78e832782d36fa/app/model/order.go#L359).
- **V, local read-only observation:** `backend/app/modules/payments/router.py:69-103` currently returns HTTP 200 `fail` for parse/rate failures and unsuccessful settlement outcomes; its docstring incorrectly says that body causes gateway retries.
- **I:** This is a high-priority reliability defect: a legitimate paid callback arriving during a transient re-query failure can be permanently acknowledged before local settlement, suppressing automatic gateway retries. The caller should return a non-200 for retryable processing failure; return 200 only for durably accepted/settled/idempotent outcomes or deliberately harmless statuses. A route-level regression should assert HTTP status and a fail-then-retry recovery. No production reproduction was attempted.
