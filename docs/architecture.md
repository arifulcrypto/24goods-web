# Architecture: 24goods

**Status:** v0.2 (MVP-0 implemented). Rationale and trade-offs for every change since v0.1 are in [review-v2.md](review-v2.md); the original platform evaluation is in [analysis.md](analysis.md).

**Priorities:**
1. Security
2. Correctness of money and stock
3. Speed from mainland China
4. Developer velocity

## 1. Runtime topology (one host: demo and the MVP-0 single-VPS layout)

**Rules:**
- Only `web` publishes a port. Docker-published ports bypass UFW, so nothing else may ever get `ports:`.
- Each container receives **only its own** env file (`deploy/env/<service>.env`, generated by `deploy/bootstrap.sh`).

## 2. Production server allocation (M1)

Unchanged in intent from v0.1:

| Host | Role |
|---|---|
| SoftBank JP | Edge / CN entry: Caddy + CrowdSec; holds no data and no keys |
| IIJ JP | Core: api, delivery, PostgreSQL, Redis |
| US UT | DR / ops: PG replica, pgBackRest repository, monitoring, restore drills; OpenBao later |
| Tencent GZ | CN probe only |

**Starting point:** one domain, standard automatic HTTPS. A second CN entry hostname is added **only if** measured CN latency justifies it.

**Latency rule:** if p99 RTT × DB round-trips exceeds 30% of the 150 ms server-side p95 budget, consider colocating the API with PostgreSQL. This is a manual decision recorded as an ADR, never automatic ([review-v2 §6.3](review-v2.md#63-latency-decision-rule-replaces-5-ms)).

## 3. Components

| Component | Implementation |
|---|---|
| API | FastAPI modular monolith: `auth`, `catalog`, `chat` (+quotes), `orders`, `payments` (notify), `inventory`, `uploads`, `realtime`, `admin`. SQLAlchemy 2 async + asyncpg, Alembic. One process serves the public app (:8000) and an internal app (:8081). |
| Delivery service | Separate process. Outbox consumer (`FOR UPDATE SKIP LOCKED`) plus a Starlette-only internal reveal API. The only holder of private keys. FastAPI/pydantic are not loaded (enforced by test). |
| Jobs | Durable work goes through the PostgreSQL **outbox** (same transaction as the state change). Order expiry runs as an asyncio task in the API. |
| Realtime | **SSE** over Redis pub/sub (`rt:*` channels), with a 15 s heartbeat; clients fall back to polling. Centrifugo is deferred until there is more than one API node or more than ~2k concurrent connections. |
| Frontend | Two static Vite SPAs in one pnpm workspace (`web`: Vant 4, `admin`: Element Plus, `shared`), served by Caddy. **No Node at runtime.** Web initial JS is 77 KB gzip (budget 150 KB). |
| Payments | `PaymentAdapter`-style ZPay adapter on the EPay protocol (`app/payments/epay.py`, `zpay.py`). USDT (BEpusdt) is phase 2. |
| Uploads | Local volume in the demo; a private R2 bucket proxied via the edge in production. Served only through `/api/v1/files/{id}` with authorization. |
| Search | PostgreSQL full-text search + `pg_trgm` |

## 4. Data model (implemented, `migrations/versions/0001_initial.py`)

Every tenant table has `tenant_id`, with **ENABLE + FORCE ROW LEVEL SECURITY** and the policy `tenant_id = current_setting('app.tenant_id')::uuid`. An `after_begin` hook pins the tenant on every transaction, and background jobs pin the tenant per job.

Tables:
- `tenants`, `users`, `agent_status`, `custom_domains`
- `products` (i18n jsonb, `price_minor`, `floor_price_minor`, `delivery_mode`)
- `card_stock` (`blob` bytea, `fingerprint`, `kid`, `status`, `order_id`)
- `conversations`, `messages` (bigserial ids, `UNIQUE(sender_id, client_msg_id)`), `attachments`
- `quotes` (HMAC-signed, versioned)
- `orders` (random `order_no`, `version`, `quote_id UNIQUE`), `order_events`
- `payments` (`UNIQUE(channel, gateway_trade_no)`, `UNIQUE(order_id)`)
- `deliveries`
- `ledger_entries` (append-only by grants; a deferred trigger enforces Σ = 0 per transaction)
- `outbox`, `audit_log`

Money is stored as `bigint` minor units plus `currency`. Floats are never used.

**Roles** (non-superusers; the superuser exists only for initdb):

| Role | Privileges |
|---|---|
| `app_owner` | Owns the schema; `CREATEROLE`; runs migrate and seed; bound by FORCE RLS |
| `app_api` | `INSERT` on `card_stock`, but **no `SELECT` on `blob`** (column grant); normal CRUD elsewhere |
| `app_delivery` | Reads `blob`; updates only `status`/`order_id`; writes deliveries, events, messages, ledger, audit |

## 5. Card-key vault and key lifecycle

- **Crypto** (`app/core/cardvault.py`): one DEK per card, AES-256-GCM. The DEK is wrapped with X25519 ECDH + HKDF-SHA256 + AES-GCM. AAD = (tenant, product, card_id), so a row swap fails to decrypt. A keyed, tenant-scoped HMAC fingerprint provides dedup.
- **Isolation, four layers:**

| Layer | API | Delivery |
|---|---|---|
| Process | `CardSealer` with public keys only; refuses to start if a private-key file is configured | `CardOpener`, the only process with private keys |
| Secret | `vault_public_keys` | `vault_private_keys`, mode 0400, owned by the container uid |
| Database | No `SELECT` on `blob` | Reads `blob` |
| Network | edge + backend | backend only, with **no egress** |

- **Reveal:**
  1. The buyer calls `POST /orders/{id}/reveal`.
  2. The API checks the session and owner, then calls `delivery:8001/internal/reveal` with an internal token (constant-time compare).
  3. Delivery re-checks the owner and the delivered state.
  4. It applies a per-order limit (10/h), a per-buyer limit, and a **global circuit breaker** (30 decrypts/min → 503 + CRITICAL log). A request larger than the remaining budget is rejected before counting.
  5. It writes an audit row and returns the codes with `Cache-Control: no-store`.
- **Lifecycle:** generate with `app.devtools.keygen` (offline in production) → distribute (public key to the API, private key to delivery only) → keep in memory only → back up with age to two offline copies (never in DB backups) → rotate (new `kid` + `rewrap()`) → on **compromise**, revoke, void unsold stock under that `kid`, re-import, notify buyers → destroy. Details: [review-v2 §4](review-v2.md#4-key-isolation-concrete-design).
- **Card import:** `POST /admin/products/{id}/cards/import` is **admin role only**, ≤5000 lines, rate-limited, audited, sealed immediately; plaintext is never echoed. Production adds TOTP step-up and an admin-only network path (M1) and two-person approval for bulk imports (M2).

## 6. Payment pipeline: ZPay Alipay v1

```
pay:    server-priced order ─► signed submit.php URL (no key in URL) ─► buyer pays
notify: GET /api/v1/pay/notify/zpay   (per-IP rate limit; bad-signature audits sampled)
  1 pinned-MD5 signature (constant time) · pid · out_trade_no · TRADE_SUCCESS · exact Decimal amount
  2 Redis replay guard: 60 s IN-FLIGHT lock → promoted to 24 h "done" only after settling
    (a crash mid-settle never blocks ZPay's retries for long)
  3 re-query api.php?act=order (≤3 s total; ZPay waits 5 s): paid, same money, same trade_no, same out_trade_no
  4 BEGIN · order FOR UPDATE · already paid → success · pending → paid
    · late (expired/cancelled, however late) → manual_review, still recorded
    · amount changed after pay URL → manual_review
    · INSERT payments (UNIQUE) · ledger Σ=0 (+ 1.6 % fee txn) · outbox(order.paid) · COMMIT
  5 "success" (also for manual_review, audited) / "fail" (bad sig, outage → ZPay retries)
return_url → display only (redirect to the order page)
```

Prod guards: the gateway and the query base must be `https://`, `APP_COOKIE_SECURE=true`, and the mock gateway refuses to run outside `dev`/`test`. M1 adds a reconciliation job that polls the query API for `pending_payment` orders with a pay attempt, plus external alerting on `manual_review`.

## 7. Chat and negotiation

```
Product "Chat"  → POST /conversations {product_id} → find-or-create + product_card snapshot
Agent "Quote"   → POST /admin/conversations/{id}/quotes → quote (HMAC, expiry, qty≤10 for auto_card) → quote_card
Buyer "Accept"  → POST /quotes/{id}/accept → TX: lock quote, verify → order(pending_payment, quote amount)
Agent "Price"   → PATCH /admin/orders/{id}/price (pending only, ≥ floor×qty, version++, audited, system msg)
Buyer "Pay"     → POST /orders/{id}/pay → ZPay → §6 → delivered (auto) | agent delivers (manual) → confirm
```

- **Message types:** text, image, voice (≤60 s, ≤1 MB, webm/ogg/mp4), product_card, quote_card, order_card, system. When a card's state changes, the server re-publishes the message under the same id, so the client replaces it.
- **Agent status:** online / away / on_hold / offline. Buyers see the best status across agents.
- **Staff Inbox:** filters (all / mine / unassigned), assign, unread counts, close, quote composer, and the buyer's recent orders.
- **Not built:** voice **calls**, which were dropped ([review-v2 §0](review-v2.md#0-what-changed-summary)).

## 8. Security controls

| Threat | Controls (✅ in MVP-0, ⏳ planned) |
|---|---|
| Card-key theft | §5 ✅ |
| Forged or replayed callbacks | §6 ✅; tests cover forged/tampered/wrong pid/downgrade/replay/concurrency/crash-mid-settle/timeout/late |
| Price tampering | Server prices; HMAC quotes; versioned, audited price changes ✅ |
| Cross-tenant access / IDOR | FORCE RLS + per-transaction pinning; owner checks with a uniform 404; cross-tenant tests ✅ |
| Session attacks | Hashed session keys in Redis, rotation on login, HttpOnly, SameSite=Lax, `__Host-` prefix over HTTPS, CSRF header ✅ |
| Brute force / CC | Redis limits: failed logins per (email, ip) + per email; register; messages; uploads; orders, pay and accept per user; ≤5 pending orders per buyer; notify per IP ✅. Edge: Cloudflare / CrowdSec ⏳ M1 |
| Malicious uploads | Magic bytes, single-format decoder, pixel caps, re-encode, EXIF stripped, random keys, `CSP: sandbox`, `nosniff`, voice served as attachment ✅. Separate media origin ⏳ M1 |
| Secret sprawl | Per-service env files, Redis ACL users, column grants, a private-key file only in delivery ✅ |
| Supply chain | SHA-pinned Actions, Dependabot with a 7-day cooldown, pip-audit / pnpm audit, Trivy, gitleaks ✅ |
| On-demand TLS abuse | `ask` endpoint: internal listener, verified domains only, normalization, negative cache, rate limit ✅ (block disabled until M4) |
| Independent audit | ⏳ **M1 exit gate**: no real money before it |

### ADR-015: List storefront, generated covers, Kesiv brand config
- **Context:** The reference shops (gmailbuy and others) sell by plain, dense lists with tags in the title; buyers of virtual goods compare price and stock, not photos. Most products have no image.
- **Decision:** The default product view is a grouped list (56 px thumbs, price, stock, Buy) with an optional grid toggle. A missing cover is a deterministic SVG generated client-side from the title and category. Every brand string lives in `packages/shared/src/brand.ts` (+ `APP_BRAND_NAME` for meta).
- **Consequences:** No image storage or generation endpoint is needed; a rename is a one-line change. Covers can't be customised server-side until a real image is uploaded.

### ADR-016: Instant accounts + self-hosted PoW instead of guest checkout
- **Context:** Guest checkout would leave chat, after-sales, reveal budgets and order history without an identity, and anonymous orders can't be rate-limited per buyer.
- **Decision:** One-tap instant account (`POST /auth/instant`): random handle and password returned once, a normal buyer row with `is_instant=true`. Abuse is limited by a self-hosted HMAC-signed, single-use proof-of-work (no third-party captcha because of China reachability and privacy), per-IP limits (3/h, 10/day), a hard per-/24 (/48) cap of 200/day with a soft ramp (+4 / +6 PoW bits above 30 / 100 accounts per net today), at most 2 pending orders, and a 7-day purge of unpaid instant accounts. Instant accounts are created without an email; an email can be added later and is unverified until email verification (M1).
- **Consequences:** Everything downstream keeps one identity model. CGNAT or office networks are slowed down, not blocked. Email ownership is unverified, so the credentials path uses a generic conflict message and the gap is a tracked known issue.

### ADR-017: Access-code order lookup
- **Context:** Lookup by order number alone is an IDOR (guessable numbers); buyers who lose instant credentials still need their codes.
- **Decision:** Every order gets a 10-char Crockford base32 access code (50 bits), stored only as `HMAC-SHA256(lookup_key, order_no || code)`. `POST /lookup` and `/lookup/reveal` need order no + code and never create a session. Order of checks: per-IP limit, verify the code, and only on failure count it per `order_no:ip` (5/h) and per order (50/h). A correct code is never blocked by the per-order counters, so nobody can lock a buyer out.
- **Consequences:** Reveal goes through the same delivery service and budgets as the signed-in path. At 50 failures/h per order, guessing 2^50 codes is infeasible. `APP_LOOKUP_KEY` is mandatory in prod; rotating it invalidates all existing codes (buyers can rotate individually).

### ADR-018: Card management without plaintext
- **Context:** Staff need to find, void and replace cards, import batches and expire them, but invariant 1 forbids plaintext outside the vault and the delivery worker.
- **Decision:** Cards carry a keyed fingerprint (content) and a `lookup_fp` (first field, case-folded), both HMACs with the vault fingerprint key. "Find" recomputes the fingerprint of what the admin pastes and matches; it never decrypts and returns masked values only. Void/replace are state changes with a reason (`defective`, `expired`, ...); batches record imports; `expires_at` drives an hourly void job. `/admin/cards/find` is audited with counts only and limited to 30/h per admin.
- **Consequences:** Find is an existence oracle for people who already hold a code, so it is admin-only, rate-limited and audited. Replacement claims fresh stock in the delivery worker and records the acting staff member.

### ADR-019: After-sales, auto-confirm and recorded refunds
- **Context:** Digital goods need a warranty window and a way to settle disputes; unconfirmed orders must not hang forever, and money movement must not be silent.
- **Decision:** `after_sales_until` and `auto_confirm_at` are snapshotted at delivery (site default 28 d / 72 h manual, 24 h auto_card; per-product override). A buyer opens one ticket per order; staff can process, replace (manual: new text; auto_card: outbox job in the delivery worker), reject, resolve; refund is admin-only and, from the 3rd replacement, replace needs an admin. Opening a ticket bumps `order.version` and pauses auto-confirm; the job re-checks for open tickets under the order lock. A refund only RECORDS the refund (order `refunded`, balanced reversal ledger entries, audit); the money goes back through the Alipay console until a refund API is integrated. Late payment notifies for a refunded order with the same trade number are acknowledged without effect.
- **Consequences:** The ledger and the gateway can diverge if staff forget the console step; reconciliation (M1) must flag it. A refunded order's cards are never revealable (409).

### ADR-020: Production edge: Cloudflare proxied + Origin CA + Authenticated Origin Pulls on port 8088
- **Context:** `shop.kesiv.com` is served from one non-mainland host behind LXD NAT. We want public TLS, DDoS absorption and a hidden origin without running ACME on the host, and the staff console must not be reachable by the whole internet.
- **Decision:** DNS is Cloudflare-proxied (SSL Full strict); an Origin Rule sends traffic to origin port 8088. Caddy there serves HTTPS with a Cloudflare Origin CA certificate and requires a client certificate (`client_auth require_and_verify`, Authenticated Origin Pulls), so a direct hit on the origin IP fails the TLS handshake. Caddy trusts `CF-Connecting-IP` only from the hard-coded Cloudflare ranges (`trusted_proxies_strict`) and passes `X-Forwarded-For: {client_ip}` to the API, which trusts only the Caddy container (10.89.10.10). `/admin`, `/admin/*` and `/api/v1/admin/*` are answered 403 unless the client IP is in `ADMIN_ALLOW_IPS`. A loopback-only `:80` site exists only for the container healthcheck. Dev and prod run the same images and base compose; prod adds an override file and a Caddyfile.
- **Consequences:** The Cloudflare IP list is static and must be refreshed (rarely changes; if stale, visitors from new ranges would be seen as Cloudflare IPs, which fails closed for the admin allowlist). Cloudflare idles out requests after 100 s; the SSE heartbeat is 15 s. The allowlist is IP-based: staff outside it need a change in `.env` plus `compose up -d web`; a VPN or Cloudflare Access is the better long-term answer. Cloudflare sees all traffic in clear text (accepted).

### ADR-021: Checkout-level payments and a buyer-paid channel surcharge
- **Context:** ZPay charges the merchant 1.6 %, and the owner wants buyers to carry a channel fee (default 3 % for Alipay) so every sale is profitable. A cart should be payable in one go, but a gateway trade maps to one `out_trade_no`, and one card-key order must still be fulfilled independently of its siblings.
- **Decision:**
  - *Surcharge.* The fee is computed server-side at order creation: `fee = ceil(subtotal * permille / 1000)` (integer maths), `amount = subtotal + fee` (DB CHECK), the rate is stored on the order (`fee_permille`) and configured in `tenants.settings.payments.channels` (default 30 permille, range 0-200). Paying with a channel whose rate differs from the stored one re-applies that channel's fee while the order/checkout is unpaid (issue 23, supersedes the original `fee_channel_mismatch` refusal): fee/amount/version are rewritten under the row lock and audited; the old pay URL / USDT attempt is not honoured because its notify amount no longer equals `amount_minor` and goes to manual review; once a `payments` row exists the switch is refused (`invalid_state`). Views expose server-computed `channel_totals` per enabled channel and the cart preview uses the same per-line ceiling. Admin price changes set the new subtotal and recompute the fee. The ledger splits a payment into `gateway_clearing +amount`, `sales_revenue -subtotal`, `surcharge_revenue -fee`; refunds mirror the lines; the 1.6 % gateway cost entry is unchanged.
  - *Checkout.* A cart creates one order per line (own order_no, access code, fee, fulfilment) plus a `checkouts` row (`C` + 12 base32) whose `amount_minor` is the sum. The gateway sees only the checkout (`out_trade_no = checkout_no`); member orders refuse to be paid directly (`pay_via_checkout`). The notify keeps the full pipeline of ADR-007 (signature, pid, exact amount against the checkout, status, re-query, replay guard) and then settles under locks taken in a fixed order (checkout `FOR UPDATE`, then orders `ORDER BY id FOR UPDATE`), with one `Payment(checkout_id)` (`UNIQUE(checkout_id)`, `UNIQUE(channel, trade_no)`). The per-order paid transition (status, events, ledger, outbox `order.paid`, `sold += qty`, chat and buyer-input messages, audit) is ONE helper (`payments/settle.py::settle_member`) shared by the single-order and checkout paths, so both behave identically. A checkout that is expired or cancelled makes every member late (manual review, money recorded, nothing fulfilled).
  - *Cancel.* Buyer and staff cancel are one code path: only `pending_payment`, a member order cancels the whole checkout, and if a pay URL was ever issued the gateway is queried first without holding locks (paid -> settle normally and answer `already_paid`; query failure -> 503), following Alipay's "query before close".
  - *Open orders cap* counts payables (pending single orders + pending checkouts), not member orders.
- **Consequences:** Buyers see one extra transparent fee line; sales stay at list price. A checkout cannot be partly cancelled or re-priced (staff close it instead). A tenant that changes the rate invalidates pending orders created at the old rate for payment (they expire or are recreated). Legacy orders have fee 0 and keep working. Fulfilment, refund and chargeback stay per order, so a refund of one member reverses only its lines. Payment lookups for an order use `order_id OR checkout_id`.

### ADR-022: Cloudflare Turnstile script is a documented exception to "no third-party runtime assets"
- **Context:** Owner wants a Turnstile shield on login/register/instant/reset/lookup. Cloudflare forbids self-hosting `api.js`; invariant 8 forbids runtime third-party/CDN assets.
- **Decision:** the frontend loads `https://challenges.cloudflare.com/turnstile/v0/api.js?render=explicit` only when `GET /site` reports `turnstile.enabled` and only on a protected form. Verification is server-side (`app/core/turnstile.py`): tokens are single use (Redis 5 min), siteverify has a 5 s timeout and fails closed; enabled-without-secret is treated as disabled so a misconfiguration cannot lock out staff. Off by default. The secret lives AES-256-GCM sealed in `tenant_secrets` (`app/core/secretbox.py`, key `APP_SETTINGS_KEY`, AAD `tenant_id|name`).
- **Consequences:** Cloudflare sees visitors of protected forms (reachable from mainland China in practice, but a block degrades to the fallback of leaving Turnstile off). CSP must allow `challenges.cloudflare.com` for script/frame/connect only on those pages. Audit retention purge goes through a bounded SECURITY DEFINER function (`purge_audit_log`, rows older than 30 days only) so `app_api` keeps no table-level DELETE on `audit_log`.

### ADR-023: USDT via self-hosted BEpusdt as three fixed channels (MVP, no provider-instance model)
- **Context:** The owner wants to receive USDT (docs/review-v5.2.md §7, research in `docs/research/bepusdt.md`). A generic "provider instances" model (v5.1 §4) is more than the MVP needs.
- **Decision:**
  - *Channels.* `usdt_arbitrum`, `usdt_xlayer`, `usdt_trc20` sit next to `zpay_alipay` in `modules/payments/channels.py` with the same `enabled` / `surcharge_permille` tenant config, **disabled by default** (surcharge default 0). Entry pricing of an order uses the first enabled channel and is re-applied at pay time as before. `settle.py` takes the channel as a parameter: `payments.channel`, `orders.channel`, ledger account `gateway_clearing:{zpay|bepusdt}` and memo `{provider} payment ...` follow it; BEpusdt has no gateway-cost entry. Refunds mirror the lines of the order's own channel.
  - *Gateway.* BEpusdt (`v03413/bepusdt:v1.24.3`) runs on its own docker network (`usdt`, shared with `api` only), with no published port and no Caddy route; its console is reached through an SSH tunnel. Adapter `payments/bepusdt.py` (config `APP_BEPUSDT_URL`, `APP_BEPUSDT_API_TOKEN` in `api.env` only). The order amount stays CNY: `create-transaction` is called in fixed-amount mode (`amount > 0`, `fiat=CNY`, `order_id = order_no | checkout_no`). Signature: upstream's MD5 scheme, pinned, compared with `hmac.compare_digest`; a notify is also accepted when the JSON floats are rendered without trailing zeros (how a Go float64 is stringified), both variants being keyed with the token.
  - *Notify.* `POST /pay/notify/bepusdt` (JSON, exempt from CSRF and the global limiter): signature -> `order_id` is an order/checkout of THIS tenant -> `status` (1 waiting / 3 expired: reply `ok`, no state change, no audit per ping) -> `amount` exact `Decimal` == order amount (else manual review) -> the order was opened on a USDT channel -> Redis replay guard -> server-to-server `POST /api/v1/pay/info {trade_id}` must say status 2, same `order_id`, same `money`, `fiat=CNY` and a `trade_type` that maps to the order's channel -> the existing settle pipeline (row lock, state machine, `UNIQUE(channel, gateway_trade_no = trade_id)`, ledger, outbox). **Known defect, #26 (2026-11-08):** the pinned upstream native POST notifier accepts any HTTP 200 and ignores its body. Current `200 fail` replies therefore suppress retries. Intended behavior is HTTP 200 only for durably accepted/idempotent or harmless outcomes, and non-200 for retryable failure; the code fix is pending. See the [pinned-source evidence](research/security-payment-audit-2026-11-08.md#f0--bepusdt-http-200-failure-replies-permanently-acknowledge-failed-callbacks). `actual_amount`, `token` (address) and `block_transaction_id` are kept in `payments.raw` (audit); the crypto amount is never trusted for money. Cancel re-queries the stored `trade_id` first (currently Redis-dependent; durable attempt storage is pending).
  - *Buyer UI.* The pay endpoint returns our own page `/pay/usdt/{no}`; `GET /api/v1/pay/usdt/{no}` (owner only) serves network, address, exact USDT amount, countdown, order status and a server-generated QR (segno, pure Python, SVG, rendered via an `<img>` data URI). The page polls the status; the BEpusdt checkout page is never exposed.
  - *Attempt state.* The BEpusdt attempt (trade_id, address, `actual_amount`, expiry) is kept in Redis (`usdt:attempt:{no}`, 7 d TTL), not a new table: it is display state and the cancel re-query key, while fulfilment re-derives everything from the gateway re-query and the order. An unexpired attempt for the same channel and amount is reused; otherwise BEpusdt rebuilds the trade for the same `order_id`.
- **Consequences:** MD5 stays weak but is bounded by the re-query over the internal network. If Redis loses an attempt the pay page 404s until the buyer presses pay again (a fresh trade is created); a payment to an old trade still settles through the notify (or lands in manual review if it was cancelled/expired). Cancelling an order does not cancel the BEpusdt trade (a later payment becomes a late payment in manual review). Switching channel after a pay URL was issued is refused when the fee rate differs (`fee_channel_mismatch`, ADR-021). Adding a fourth network is a one-line change in `USDT_CHANNELS`. Network: `api` and `bepusdt` share the `usdt` network so the notify can reach `api:8000`; bepusdt can then also reach the api's internal listener (:8081, read-only rate-limited TLS ask) — accepted (security review 2026-11-07). The image is pinned by digest (Docker Hub has no semver tags: v1.24.3 = `0716485`).

### ADR-024: Crawler/first-paint HTML rendered by the API, SPA stays (supplements ADR-009)
- **Context:** The international store needs SEO (review-v5.2 §6): per-page title/description/canonical/hreflang/Open Graph/JSON-LD and real content for crawlers and link previews, a sitemap, robots and honest 404s. ADR-009 keeps static Vite SPAs with no Node at runtime; Nuxt SSR would add a runtime and a second renderer of the same pages.
- **Decision:**
  - Module `app/modules/seo` serves, **at the site root** (not `/api`), exactly `/`, `/p/{id}`, `/a/{slug}`, `/help`, `/search`, `/sitemap.xml`, `/robots.txt`. Caddy (`Caddyfile`, `Caddyfile.prod`) matches only those paths and proxies them to `api:8000`; assets and every other SPA route stay static.
  - The API takes the **built SPA `index.html` as the template** (fetched from Caddy's `web` container over the internal edge network as `http://web/index.html`, i.e. `APP_WEB_INDEX_URL`; `APP_WEB_INDEX_PATH` reads a file instead; cached 60 s, stale-if-error). It strips the template's title/description/OG/robots tags, injects the per-route head, and puts a pre-rendered content block inside `<div id="app">` (Vue replaces it on mount, no hydration). Chosen over baking the file into the API image (two images would have to be built in lockstep) and over a shared volume (extra mount, ordering).
  - A site block `http://web` (demo) / host `web` on the container-internal `:80` (prod) serves `/index.html` only. If the API is down or answers 502/503/504, Caddy serves the static shell, so the SEO layer is never a single point of failure.
  - Safety: all values HTML-escaped; JSON-LD via `json.dumps` with `<`, `>`, `&` escaped; description/body HTML only from the existing sanitized markdown fields (`core/markdown.py`); product lookup by UUID only, tenant-filtered, status `active`, disabled categories and reseller-hidden products are 404; no auth, no cookies; canonical hosts come from the public base URL or a host resolved to a tenant/reseller domain, never a raw Host header. Language = `?lang=` (else tenant default locale), never `Accept-Language`, so a URL has one content; the SPA honours `?lang=`.
  - Unknown product/article: HTTP 404 with the SPA shell, `noindex,nofollow`, no canonical/JSON-LD. Unknown static SPA paths stay 200; the SPA renders a designed 404 page and sets `noindex` itself.
  - Setting section `seo` (`indexing_enabled` default true, `index_storefronts` default false, `default_description_i18n`, `og_image`). Indexing off or a white-label storefront host (unless `index_storefronts`) means `noindex,nofollow` on every page, `X-Robots-Tag`, `robots.txt` = `Disallow: /` and an empty sitemap.
  - The global per-IP limiter also covers these root paths (it covered `/api` only).
- **Consequences:** No new runtime or service; one more internal fetch of a small file per minute. Content is rendered twice (this module and the SPA): keep the fallback block simple. HTML is `Cache-Control: public, max-age=0, s-maxage=300, must-revalidate` (not `max-age=300`: the shell embeds hashed asset URLs that a deploy removes); sitemap/robots use `public, max-age=300`, the sitemap is also cached in-process for 10 minutes. There are no category URLs yet (the SPA filters categories client-side), so none are in the sitemap. Mobile/JS-less crawlers get the product title, description, price and links; Google's JS renderer still sees the SPA after Vue mounts.

### ADR-025: Versioned payment providers, typed presentation and optional payment challenge

- **Status:** Proposed, 2026-11-08; requirements documented, no implementation or provider compatibility approval implied.
- **Context:** A single ZPay/Alipay client and fixed channels do not cover multiple EPay instances, native vendor protocols and local QR display. An authenticated upstream can still be compromised or misconfigured. Current payment initiation has no configurable challenge; #26 records prerequisites that need repair.
- **Proposed decision:** Separate provider instance/configuration version from payment method; bind every durable attempt to its original merchant, exact amount/currency, credential version, upstream transaction and presentation. Use protocol-specific adapters and one settlement pipeline. Native QR/redirect/deep-link are explicit presentation types; keep credentials server-side. Validate provider ownership/permissions and reconcile independently where needed. Add an optional server-enforced challenge for payment creation with atomic attempt-bound consumption and bounded self-hosted difficulty; do not challenge callbacks or recovery.
- **Consequences:** Configuration rotation must drain old obligations; unknown provider-create results require query/reconciliation rather than blind retries. Local QR can avoid some redirects but cannot guarantee domain/provider anonymity or bypass merchant restrictions. Xiaodou remains unverified pending authorized contract documentation. Requires payment/security/mobile review and staging contract tests. Detailed design: [v6 §§1–3](review-v6-payments-ops.md).

### ADR-026: Restricted operations visibility, complete recovery and manual-service reminders

- **Status:** Proposed, 2026-11-08; no monitoring service, backup schedule or reminder job installed.
- **Context:** Existing business stats/audit and container log rotation are useful but do not prove host health, completed recoverable backups or recurring-service expiry management. Current backup script lacks encryption/whole-set completion and BEpusdt state coverage.
- **Proposed decision:** Extend admin with a small role-restricted overview plus structured login/system/task/payment events, key/software maintenance metadata and bounded alerts. Collect host metrics without Docker/LXD sockets or delivery secrets. Back up complete versioned encrypted sets off-host, with isolated restore/reconciliation proof and explicit RPO/RTO. ### ADR-025: Versioned payment instances and durable private attempts

Context: one process-wide EPay key and Redis-only USDT display state cannot safely represent rotation, uncertain creation or independent upstream retries.

Decision: keep the existing internal `zpay_alipay` channel for stored-data compatibility while separating immutable tenant provider versions and encrypted keys from the payment method. Reserve attempts durably before I/O; bind old callbacks/queries to their original configuration. Generate local QR SVG from validated typed payloads, expose only owner-authorized views, and settle through the existing locked ledger/outbox path. USDT attempts retain encrypted original gateway credentials, exact address and crypto amount; a changed receiver is a review hold.

Consequences: EPay-compatible Alipay is configurable; native RSA/Lantu/official Alipay interfaces need distinct documented adapters and approval. Database/settings-key recovery is required when old versions drain. Local QR reduces redirects but does not hide the storefront/upstream from QR contents, wallets, receipts or payment infrastructure. Valid signatures and same-provider queries cannot independently establish honest settlement.

### ADR-026: Small operational surface and manual service periods

Context: staff needs resource/log/recovery visibility and monthly top-up reminders without giving the API a root hosting panel or recurring debit authority.

Decision: expose bounded read-only process/cgroup/filesystem and tenant summaries to platform administrators, sanitized events, and optional allowlisted recovery marker metadata. No daemon socket/root mount/terminal is introduced. Track tenant service periods from explicit activation; verified payment plus staff completion extends a separate renewal once. Use durable versioned reminder schedules and bounded external retries with stable IDs.

Consequences: missing host/restore evidence stays unknown. SMTP/TG has uncertain-send duplication risk; scheduling uniqueness is not exactly-once external delivery. Backups fence writers, encrypt whole sets with age and independently protect vault recovery keys; they cause a maintenance interruption and do not implement PITR. Real restore drills, off-host alerts and production policy remain operational release gates.

### ADR-027: Record legacy pay URLs; the record adds checks, never removes them

Context: the environment-key EPay path signed a `submit.php` URL and recorded nothing, so every later decision about whether money could still arrive through it — chiefly whether a cancel is safe — was inferred from the current channel, key presence, cutover time or provider history. All four can change after the URL is issued. An independent payment audit (2026-11-08) showed the inference failing both ways: cancels proceeding over a live legacy URL after a channel switch, a provider cutover or full de-configuration (fail-open), and every EPay cancel returning 503 for a tenant on durable providers with no env key (fail-closed false positive).

Decision: write a `legacy_pay_urls(tenant_id, local_ref)` row in the transaction that commits before the URL is returned; it is RLS-enforced and append-only for `app_api`. A migration backfill marks every payable pending at deploy time. On cancel, a recorded URL is always queried, whatever the channel or provider history, and fails closed (503) when the signing key is gone. With no record and no key, the cancel proceeds. With no record and a key present, the earlier best-effort query (v4 review W2/W3) is kept. The record adds certainty but never removes a check. In the same pass, reconciliation carries committed outcomes through any exception type, collects them in a caller-owned sink so a `wait_for` timeout cannot lose them, marks an attempt settled inside the settlement's own commit, and alerts on every distinct duplicate trade.

Consequences: the backfill over-marks (USDT and durable-provider payables included), so on a deployment with no env key a payable pending at deploy time cannot be cancelled manually; it returns 503. This is bounded: every order and checkout gets an `expires_at` from the tenant TTL at creation, and the expiry job does not pass through the cancel gate, so these expire on schedule. Only rows that predate expiry altogether could be held longer. The cost is deliberate: under-marking would allow cancels over money. The pay flow re-checks that the payable is still pending after the marker commits, so a cancel that completes inside the pay window never leaves a URL in the buyer's hands. Late legacy notifies for a payable that also has a durable attempt are still rejected into manual review, so a paid legacy URL is caught by cancel or by staff, never silently dropped. Unexpected reconciliation errors now become 503 (logged with traceback) rather than 500, and one failing ref no longer aborts the tick for the remaining tenants.

### ADR: subscription products and month-based after-sales (review-v7)

Context: staff typed UUIDs to track monthly services by hand, and the after-sales default was a fixed 28 days that never matched a monthly billing cycle.

Decision: a product carries an optional `subscription` config and an optional `after_sales_months`; resolution is product hours, product months, tenant `after_sales_default` (legacy hours key honoured), built-in 1 month. Calendar-month arithmetic lives in `sitedefaults.add_months` (UTC, clamped to month end) and is shared with `operations.service.periods_end`. A periodic API job `sync_subscriptions` (not the delivery worker, which has no grants on service tables) creates or extends services from delivered orders using the existing unique `(tenant_id, order_id)` constraints for idempotence, and cancels auto services whose source order was refunded or cancelled. `service_entitlements` gains `product_id` and `source` (manual/auto).

Consequences: months are an approximation (x720 h) only in the legacy `after_sales_hours` view; the order's `after_sales_until` stays authoritative. The delivery worker only passes `product_months` into `delivery_deadlines`. No recurring charge and no buyer-side renew button; renewals still require a separate paid order.


### ADR: order, stock, refund and subscription integrity (review-v8, issue #59)

Context: the last auto-card could be sold twice (stock was only checked, not reserved, so the second paid order landed in `manual_review` with no way out); "refunded" only recorded a ledger entry, not that the money went back; a refunded subscription renewal left the full service period in place; the reseller balance ignored open disputes; manual stock release returned `qty` even when the stock had been unlimited at order time; and an order's after-sales/subscription terms followed later product edits.

Decision: (A) auto-card stock is reserved by count: creation takes the product row lock (after the buyer row, before the promo row) and requires `available - reserved >= qty`, with `reserved` derived from orders in `pending_payment`/`paid`, so expiry and cancellation release it without extra state. Held orders get an admin-only `requeue-delivery` that re-verifies a succeeded payment covering the order, an open ledger posting and stock, then re-emits `order.paid` under a per-requeue outbox key. Paid-undelivered goods orders can be refunded by an admin through the same routine as after-sales, and buyers can escalate `not_received` once the delivery ETA (1 h for auto-card) has passed. (B) Every refund requires a 3-200 character `reference` (staff confirm the money was already returned); it is stored in the `refunded` order event, the audit detail and shown to the buyer. No new states: a two-phase refund with provider APIs belongs to #55. (C) `sync_subscriptions` reverses refunded renewals period by period (`service_renewals.reversed_at`) and a refunded source order only cancels the service when no paid renewal remains (otherwise `source_reversed_at` and one period is taken back); an ambiguous subtraction (would end before the start) is left untouched and recorded once as an operation event. (D) `reseller.balances` holds back markup of orders with an `open`/`processing` ticket (`disputed_minor`). (F) `orders.terms` snapshots after-sales hours/months and the subscription config at purchase; legacy rows (NULL) fall back to the product. (G) `orders.stock_reserved` records what was actually reserved; release gives back exactly that and zeroes it.

Consequences: a refund of a `manual_review` order only reverses the ledger when a payment posting exists (payment anomalies may have none). Reservation counts paid-but-undelivered auto-card orders until the worker consumes the cards, so a stalled worker temporarily shrinks sellable stock rather than overselling. Migration `0015_order_integrity` is additive; the delivery worker only reads `orders.terms` under its existing table-level SELECT, and app_api gains UPDATE on `service_renewals`.


### ADR: every order is visible to customer service; avatars (review-v8b, issue #58 §3-§5)

Context: a buyer who never opened chat had no conversation, so their order had no order card or system messages and the desk only chimed for paid manual orders; chat showed an avatar only for the other side and users had no picture.

Decision: order creation (buy-now, checkout, reseller sign-up) attaches the order to the buyer's open conversation and creates it when missing (`chat.conversation_id_for_order`, the idempotent `ensure_open_conversation`; staff accounts never get one). A new order card counts as unread for staff. The desk alerts on order created / paid (any delivery mode) / cancelled / expired from the existing staff `order` events, one alert per (order, event) with per-agent localStorage toggles (expired off). Avatars: `users.avatar_key` (migration `0016_user_avatars`) is the storage key of a file re-encoded by the hostile-upload pipeline to a 256 px square (input <= 2 MB, images only, EXIF dropped); no Attachment row. `GET /avatars/{user_id}` serves it with the file-endpoint headers (sandbox CSP, nosniff, same-origin CORP) only inside the viewer's tenant: own avatar, any avatar for staff, a staff avatar for buyers that staff member wrote to. Everything else is 404.

Consequences: orders created without prior chat leave a visible open conversation per buyer; the avatar file is deleted on replace, removal and account deletion; cached avatar URLs carry `?v=<key prefix>` so changes show up at once.
